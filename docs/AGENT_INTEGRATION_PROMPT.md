# Agent Integration Prompt

A single, copy-pasteable prompt for any AI coding agent (Cursor, Claude
Code, GPT-5/Codex, Cline, etc.) to wire a brand-new site into Studio CMS
end-to-end. It also works as a step-by-step **manual** checklist for a
human developer.

> Keep this file alongside Studio. When you open a new site repo, drop
> this prompt + the `studio-cms.ts` SDK into the agent's context. The
> agent has everything it needs to finish the integration without a
> human writing any glue code.

---

## How to use this with an AI agent

1. Open the **new site's repo** in your editor.
2. In Studio → workspace → **Integration**, copy the env block for your
   framework and have it ready (you'll paste it in step 4 below).
3. Open a chat with the agent and paste:

   > Read `docs/AGENT_INTEGRATION_PROMPT.md` from the Studio repo (or use
   > the inline version below). Then integrate this new site with Studio
   > CMS following the playbook exactly. Stop only when the verification
   > checklist passes.

4. Paste the env block when the agent asks for it.

If you prefer to do it manually, follow the same numbered steps.

## Inline prompt (paste this if you don't want to share a file path)

````md
You are integrating a new public site with the Studio CMS. Studio is a
multi-tenant Next.js 15 + Supabase headless CMS. The public site is the
**presentational** layer: every page is statically rendered from content
fetched at **build time** from Studio's public REST API. Run-time DB
access from the public site is forbidden — keep things static, fast, and
SEO-perfect.

You will follow this playbook **in order** and only stop when the
verification checklist at the end passes. Do not invent endpoints,
schemas, or env-var names — they are fixed below.

## 0. Get oriented

Detect the framework of the repo (Vite + React, Astro, Next.js, etc.) by
reading `package.json` and the build scripts. The integration is slightly
different per framework; the *content shape* and *API* are identical.

## 1. Install / vendor the SDK

The SDK is a single ~150-line TypeScript file with zero dependencies.

- Preferred: copy `studio/packages/sdk/studio-cms.ts` from the Studio
  repo into `src/lib/cms.ts` of this site.
- If the repo already has a `src/lib/cms.ts` or equivalent, **read it
  first** to avoid duplicating types/exports.

Surface: `createCmsClient({ baseUrl, site, apiKey })` returns an object
with `.list(type, opts?)`, `.get(type, slug)`, and `.site()`.

## 2. Wire env-vars

Add a section to `.env.example` (copy from Studio → Integration page).
Variable names — use these exact names:

| Framework    | CMS base                | CMS site slug        | API key             | Forms URL                    | Forms site             | Turnstile public          |
| ------------ | ----------------------- | -------------------- | ------------------- | ---------------------------- | ---------------------- | ------------------------- |
| **Vite**     | `VITE_CMS_URL`          | `VITE_CMS_SITE`      | `VITE_CMS_API_KEY`  | `VITE_FORMS_URL`             | `VITE_FORMS_SITE`      | `VITE_TURNSTILE_SITE_KEY` |
| **Astro**    | `CMS_URL`               | `CMS_SITE`           | `CMS_API_KEY`       | `PUBLIC_FORMS_URL`           | `PUBLIC_FORMS_SITE`    | `PUBLIC_TURNSTILE_SITE_KEY` |
| **Next.js**  | `NEXT_PUBLIC_CMS_URL`   | `NEXT_PUBLIC_CMS_SITE` | `CMS_API_KEY`     | `NEXT_PUBLIC_FORMS_URL`      | `NEXT_PUBLIC_FORMS_SITE` | `NEXT_PUBLIC_TURNSTILE_SITE_KEY` |

`CMS_API_KEY` is **server-only** — never bundle it into client-side JS in
Next.js. In Vite/Astro static sites it's only used at build time inside
`scripts/fetch-content.ts`, which runs in Node before the bundler sees it.

## 3. Write the build-time fetch script

Create `scripts/fetch-content.ts`. Output a typed module so the bundler
tree-shakes anything unused:

```ts
import { writeFile, mkdir } from "node:fs/promises";
import { dirname, join } from "node:path";
import { createCmsClient } from "../src/lib/cms";

const cms = createCmsClient({
  baseUrl: process.env.VITE_CMS_URL ?? process.env.CMS_URL ?? process.env.NEXT_PUBLIC_CMS_URL!,
  site: process.env.VITE_CMS_SITE ?? process.env.CMS_SITE ?? process.env.NEXT_PUBLIC_CMS_SITE!,
  apiKey: process.env.CMS_API_KEY ?? process.env.VITE_CMS_API_KEY,
});

const out = join(process.cwd(), "src/data/cms.generated.ts");
await mkdir(dirname(out), { recursive: true });

const [posts, cases, faqs] = await Promise.all([
  cms.list("blog-posts", { limit: 500 }),
  cms.list("case-studies", { limit: 500 }),
  cms.list("faqs"),
]);

const file = `// AUTO-GENERATED by scripts/fetch-content.ts — do not edit.
export const BLOG_POSTS = ${JSON.stringify(posts.data, null, 2)} as const;
export const CASE_STUDIES = ${JSON.stringify(cases.data, null, 2)} as const;
export const FAQS = ${JSON.stringify(faqs.data, null, 2)} as const;
`;
await writeFile(out, file);
console.log(\`✔ blog \${posts.data.length}  cases \${cases.data.length}  faqs \${faqs.data.length}\`);
```

Add `tsx` as a devDependency if missing, then chain it before the build:

```jsonc
// package.json scripts
"prefetch": "tsx scripts/fetch-content.ts",
"build":    "npm run prefetch && <existing-build-command>",
```

For Next.js you may skip the prefetch step and call `createCmsClient`
directly inside Server Components with `export const revalidate = 60`.

## 4. Hybrid content — keep legacy posts working

Most repos already have static content (e.g. `BLOG_POSTS_LEGACY` in
`src/data/`). **Do not delete** these. Build a hybrid module that prefers
CMS content but falls back to legacy when CMS is empty or missing a slug:

```ts
// src/data/blog-posts.ts
import { BLOG_POSTS as CMS } from "./cms.generated";
import { BLOG_POSTS as LEGACY } from "./blogPostsLegacy";

export const BLOG_POSTS = [...CMS, ...LEGACY.filter(l => !CMS.find(c => c.slug === l.slug))];
export function findPost(slug: string) {
  return BLOG_POSTS.find(p => p.slug === slug);
}
```

This makes the cut-over instant and reversible — flip an env var or
delete the prefetch step to revert.

## 5. Wire the forms endpoint

Find any existing contact form in the repo and rewrite its `onSubmit` to
POST JSON to the Supabase Edge Function. The exact shape is:

```ts
const res = await fetch(import.meta.env.VITE_FORMS_URL, {
  method: "POST",
  headers: { "content-type": "application/json" },
  body: JSON.stringify({
    site: import.meta.env.VITE_FORMS_SITE,
    form: "contact",        // any short id; appears in Submissions list
    name, email, message,
    turnstileToken,         // from <Turnstile siteKey={...} />
  }),
});
if (!res.ok) throw new Error((await res.json()).error ?? "Failed");
```

Add Cloudflare Turnstile widget rendering if the site doesn't already
have it. Server-side validation is done inside the Edge Function — the
form just needs to send `turnstileToken`.

## 6. SEO + sitemap

- Generate `<title>`, `<meta name="description">`, and OpenGraph tags
  from each item's `seo` jsonb field (`seo.title`, `seo.description`,
  `seo.og_image`). Fall back to top-level `title` / `excerpt` if missing.
- Generate `sitemap.xml` from `BLOG_POSTS` and `CASE_STUDIES` in
  `src/data/`. Set `<lastmod>` to `updated_at`.
- Slugs are stable; if Studio warns about a slug change on a published
  item, add a 301 redirect at the CDN.

## 7. Set up the deploy hook

The site's host needs a POST-able deploy hook URL. The user will create
the hook in their host's dashboard (Vercel / Amplify / Netlify /
Cloudflare / Render). Once they have the URL, they'll paste it into
Studio → workspace → Settings → "Deploy hook URL". You don't need to do
anything for this step in code — but **remind the user** in your final
message.

## 8. Verification checklist (must all pass)

- [ ] `npm run prefetch` succeeds locally with the new env vars; writes
      `src/data/cms.generated.ts`.
- [ ] `npm run build` succeeds.
- [ ] `npm run lint` and `tsc --noEmit` are clean.
- [ ] A test article published in Studio appears on the rebuilt site.
- [ ] A test contact-form submission shows up in Studio → Submissions.
- [ ] Legacy posts that are NOT in the CMS still render at their old
      URLs (no 404s).
- [ ] Sitemap includes both CMS and legacy entries.

If any item fails, fix it before reporting "done". The user should be
able to click "Publish" in Studio and see the change on their site within
~1 minute (rebuild + propagation).

## 9. Hand-off

Write a short summary for the user with:
- The exact files you created or modified.
- The env vars they need to set in their host's dashboard.
- The deploy-hook URL they need to paste into Studio Settings.
- Any TODOs you couldn't complete (e.g. designs for new components).
````

## Reference: API surface the agent will use

All endpoints are under `https://<your-studio>/api/v1/sites/<site-slug>/`.
Authorization: `Bearer <api-key>` when at least one key exists; otherwise
open read-only.

| Resource         | List endpoint     | Single                    |
| ---------------- | ----------------- | ------------------------- |
| Blog posts       | `/blog-posts`     | `/blog-posts/{slug}`      |
| Case studies     | `/case-studies`   | `/case-studies/{slug}`    |
| Testimonials     | `/testimonials`   | —                         |
| FAQs             | `/faqs`           | —                         |
| Pages            | `/pages`          | `/pages/{slug}`           |
| Immigration pathways | `/pathways`   | `/pathways/{slug}`        |
| Pricing tiers    | `/pricing`        | —                         |
| Bulk tiers       | `/bulk-tiers`     | —                         |
| Services         | `/services`       | `/services/{slug}`        |

List endpoints accept `?limit`, `?offset`, `?slug`, `?category`, `?tag`.

Form endpoint:

```
POST  https://<project>.functions.supabase.co/submit-form
Body: { site, form, ...any fields, turnstileToken }
```

## Reference: content shape (subset)

```ts
type BlogPost = {
  id: string;
  slug: string;
  title: string;
  subtitle?: string;
  excerpt?: string;
  cover_image_url?: string;
  body_html: string;     // already-rendered HTML from the rich editor
  body_json: unknown;    // TipTap JSON if you need to re-render
  author?: { name: string; avatar_url?: string };
  category?: string;
  tags?: string[];
  reading_time_minutes?: number;
  seo?: { title?: string; description?: string; og_image?: string };
  custom_fields?: Record<string, unknown>;
  status: "draft" | "scheduled" | "published" | "archived";
  published_at: string | null;
  created_at: string;
  updated_at: string;
};
```

`case-studies`, `pages`, `services`, etc. follow the same envelope with a
few resource-specific fields (e.g. `client_name`, `industry` on case
studies). The agent can introspect by hitting the list endpoint once and
inspecting the first item.

## Reference: tone & quality bar

- Don't change the visual design of the existing site — only rewire the
  data source.
- Preserve every legacy URL (`/blog/<slug>`, `/case-studies/<slug>`).
- No client-side fetches for primary content. SSG / build-time only.
- No `any` types in new TS code.
- No new top-level dependencies unless strictly necessary (`tsx` is the
  one allowed exception).

When all of that holds, the integration is "done".
